# 《命运石之门》0.1.4 性能记录与暂停说明

记录日期：2026-10-12。作者：xuanyide；整理与工程分析：Codex。

## 当前结论

维护者最新反馈为“可以下载，但是依旧卡顿”；此前反馈确认安装成功。该反馈未提供固件性能日志、精确耗时或全流程记录，因此不能宣布启动崩溃已经彻底解决，也不能把现有版本称为流畅稳定版。按维护者要求，本次公开保存 0.1.4 源码、准确安装包及验证记录，随后暂停本项目的移植和性能优化。未新增运行时代码或更换安装包。

## 卡顿原因推断

1. **跨脚本宏调用与小缓存叠加，可能产生频繁读取和解析。** 当前仍解释 MACROSYS、MACROSYS2、MAIN00 与剧情脚本。剧情、图像状态宏反复切换，而缓存只有三块；缓存未命中后需要异步文件读取和 JSON 解析。代码可以确认存在这些路径，现有计时也显示减少分发后端到端耗时没有改善，但尚未取得实机 I/O 轨迹，不能认定这是唯一瓶颈。
2. **原作演出计算仍占较大比例。** 为避免背景错位、无脸立绘和路线错误，转换器保留了图像缓冲交换、坐标、表情及其变量计算。即使输出是静态图文，也仍执行大量桌面引擎演出宏。现有优化只合并已验证安全的赋值和常量，未将整段演出编译成直接的场景状态更新。
3. **安全跳跃必须推进状态，不能只定位下一段文字。** 手机开放时段、邮件回复与结局标志会在过程内变化；跳跃需要停在可操作点。长章节包含更多调用、状态更新和资源切换。单次执行受时间预算限制以便让出界面，调度与跨块回调也增加总等待时间。
4. **内存约束限制了通过大缓存换速度的空间。** 字库、图片图层、脚本对象、存档和历史共同占用运行内存。0.1.4 为响应先前启动返回桌面的反馈缩小缓存并改用按需读取；较少常驻对象可能换来更多 I/O。启动崩溃没有固件日志，内存压力只是合理怀疑，尚未证实 OOM。

## 为什么其他移植应用相对轻量

此前若干项目更多采用预转换的文本、选项和场景更新记录。本项目为了恢复《命运石之门》的手机交互及原作背景／立绘语义，采用较完整的 SC3 状态机，带调用栈、寄存器、图像缓冲和跨脚本宏。差异首先在运行时工作量，而不只是包体大小。不能仅凭“其他应用不卡”排除本项目的解析、调度或内存瓶颈。

## 已验证范围

35 项回归通过；六条结局的 137,550 个可见帧、选项和 VM 状态与优化前逐帧一致；六路线按需读取及 829 次手机交互检查通过。官方模拟器完成安装、旧档迁移、冷启动恢复、长文本与邮件滚动、通讯录变化等检查。未穷举全部邮件组合，也未完成实机逐句和全结局验证。原有报告按其生成时点保留；最新实机反馈见 `reports/publication-status.json`。

## 暂停后的后续方向

以下仅记录建议，当前不继续实施：先采集实机分块命中率、读取／解析耗时和可用堆；再研究把无剧情副作用的宏编译为场景更新，以逐帧差分验证保留选项与手机状态；必要时重新安排分块边界和常驻小型宏。旧存档的原指令位置、预算语义及兼容映射应作为约束。没有这些证据前，不继续盲目压缩图片或删除演出指令。

标题仍为静态原作图片，旋转动画暂缓。现有安装包、存档键和 runtime3 格式保持不变。若应用无响应，优先使用系统返回或重启手表；重装可能清除存档，恢复出厂设置不应作为第一步。
